**7. State-credit reduction: the statute reduces the federal credit by credits allowed "on any State tax return of the taxpayer" — the donor's own State return(s), not the SGO's State.**
- (a) The reduction logic must be driven by the donor's State tax situation, not by "is the SGO in Texas". Under the proposed regulations the credit is the lesser of (qualified contributions minus State credits, not below zero) and $1,700. A "State credit" is a tax credit offered by a State for a contribution to an SGO that is allowed on a State tax return of the taxpayer; carryforward/carryback amounts count as allowed in the year of the contribution.
- (b) Quote (statute): "The amount allowed as a credit under subsection (a) for a taxable year shall be reduced by the amount allowed as a credit on any State tax return of the taxpayer for qualified contributions made by the taxpayer during the taxable year." Quote (proposed reg): "The term State credit means any tax credit offered by a State for making a contribution to an SGO that is allowed on a State tax return of the taxpayer (whether or not such return is filed jointly with a spouse) for the taxable year."

**52. Truemed webhook security and delivery rules.**
- (a) Signed mode (recommended): header `x-truemed-signature: t=<unix seconds>,v0=<hex>`; `v0` is HMAC-SHA256 hex over the string `{t}.{raw_body}`; body is an envelope `{webhook_delivery_id, event_type, data}`; `webhook_delivery_id` (prefix `dlv_`) is stable across retries and is the idempotency key; suggested staleness tolerance 5 minutes. Unsigned legacy mode: shared secret sent in `x-truemed-api-key`, flat body. Any 2xx acknowledges ("`204 No Content` is conventional"); failures are "retried with backoff for up to 7 days"; delivery is therefore at-least-once (my characterization; the docs do not use that phrase). The signature and timestamp "change on each retry attempt", so only `webhook_delivery_id` may be used to dedupe. Adding fields is non-breaking; a new enum value is treated as breaking and announced in the changelog.
- (b) Quote: "The signed payload is the string `{t}.{raw_body}` — the timestamp from the header, a literal period, and the raw request body bytes." / "Non-2xx responses, timeouts, and connection errors are treated as failed deliveries and retried with backoff for up to 7 days."

### E. Standard Webhooks (the format to implement for our own outbound webhooks)

**56. Three headers, exact lowercase names.**
- (a) `webhook-id` (unique message id, same across retries), `webhook-timestamp` (integer Unix seconds of the attempt — it changes on each retry), `webhook-signature` (one or more signatures, space-delimited).
- (b) Quote: "All of the headers should be prefixed with `webhook-` and follow the exact naming as below." / "`webhook-timestamp`: integer unix timestamp (seconds since epoch)." / "The signature header is a space delimited list of signatures associated with this webhook."
- (c) https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/spec/standard-webhooks.md (spec "Version: 1.0.0", Apache 2.0; saved `standard-webhooks-spec.md` lines 246-268). The site https://www.standardwebhooks.com/ links to this file as "THE SPEC" (saved `standardwebhooks_home.txt`).
- (d) [secondary/web] (the specification itself)

**57. Signed content and the symmetric scheme (`v1`).**
- (a) Sign the exact bytes `"{msg_id}.{timestamp}.{payload}"` (payload = raw body as sent). Symmetric: `signature = base64(HMAC-SHA256(key=secret, msg=...))`, sent as `v1,<base64>`. The secret is random, 24 to 64 bytes, presented base64-encoded with the prefix `whsec_`; the HMAC key is the base64-decoded part after the prefix. Symmetric secrets must be unique per endpoint.
- (b) Quote: "signature = base64(HMAC-SHA256(key=secret, msg="msg_id.timestamp.payload"))" / "Signing secret | Random. Between 24 bytes (192 bits) and 64 bytes (512 bits)" / "Symmetric signing keys must be unique per endpoint."
- (c) `standard-webhooks-spec.md` lines 139-146, 174-180, 198-206, 240.
- (d) [secondary/web]

**58. Asymmetric scheme is now `v2a` (ed25519 over the SHA-256 hash, with an endpoint id in the signed content); `v1a` is deprecated.**
- (a) If we ever offer public-key verification: signed content is `"{endpoint_id}.{msg_id}.{timestamp}.{payload}"`; `signature = base64(ed25519_sign(private_key, SHA-256(content)))` over the raw 32-byte hash; keys serialized as `whsk_` (secret) / `whpk_` (public); header value `v2a,<base64>`. The endpoint id is not sent with the webhook. This differs from older write-ups of the spec that describe `v1a`.
- (b) Quote: "Earlier versions of this specification defined `v1a` ... It has been deprecated in favor of `v2a`" / "Signature identifier | `v1` | `v2a`"
- (c) `standard-webhooks-spec.md` lines 174-180, 208-236.
- (d) [secondary/web]

**59. Verification rules for consumers (and therefore what our docs and SDK snippet must say).**
- (a) Use the raw body, never re-serialized JSON; constant-time comparison; accept if any signature in the list matches (supports zero-downtime secret rotation); reject timestamps outside a tolerance; use `webhook-id` as the idempotency key. The spec does not fix a tolerance value; the reference Python library uses 5 minutes in both directions.
- (b) Quote: "Make sure to verify the `webhook-timestamp` header has a timestamp that is within some allowable tolerance of the current timestamp to prevent replay attacks." / "Use the `webhook-id` header as an idempotency key" / library: "webhook_tolerance = timedelta(minutes=5)"
- (c) `standard-webhooks-spec.md` lines 168, 258-260, 270-279; reference library https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/libraries/python/standardwebhooks/webhooks.py (saved `stdwebhooks_lib/libraries_python_standardwebhooks_webhooks.py`).
- (d) [secondary/web]

**60. Payload recommendations.**
- (a) JSON body with `type` (full-stop-delimited, e.g. `user.created`; identifiers limited to `[a-zA-Z0-9_]`), `timestamp` (ISO 8601, when the event occurred), `data`. Keep payloads under about 20 kb. "Thin" payloads (ids only, consumer fetches the rest) give access control and auditability. **[FACT-CHECK]** The earlier text said "the spec calls this out for sensitive data"; the spec does not use that phrase. Its wording is "In many scenarios, it's preferable (if not required) to have an audit log for when certain data is accessed" (line 115). Applying that to income data is our design choice, not a spec requirement. The spec also says it "does not dictate the structure, or impose any requirements, on the shape, format, and content of the payload" (line 49): `type` / `timestamp` / `data` are recommendations.
- (b) Quote: "`type`: a full-stop delimited type associated with the event." / "it's recommended to keep the size of payloads small, usually smaller than 20kb" / "With full payloads, the data is just sent to every listening endpoint, with thin payloads it's required that people explicitly query the data they need, making it possible to make access auditable and more restricted."
- (c) `standard-webhooks-spec.md` lines 51-72, 115-121, 285-291.
- (d) [secondary/web]

**61. Delivery rules recommended by the spec.**
- (a) Success = any 2xx. `3xx` = failure (do not follow redirects). `410 Gone` = disable the endpoint. `429`, `502`, `504` = throttle. Honor `retry-after`. Request timeout 15 to 30 s. Retry with exponential backoff and jitter over multiple days; example schedule: immediately, 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 14 h, 20 h, 24 h. After long failure, notify by another channel (email) and disable. The spec also discusses HTTPS-only endpoints, SSRF protection (proxy that blocks internal IPs, isolated subnet), optional static source IPs, multiple endpoints per customer, a failure log with manual replay, and an endpoint-management API. **[FACT-CHECK]** Strength of wording differs by item: HTTPS is "it may be advisable to ensure that all webhook endpoints are HTTPS" (line 339) — advisable, not mandated by the spec; static IPs are "not strictly a requirement" (line 343); multiple endpoints, failure visibility/replay and a management API sit under "additional functionality that is not a core requirement" (line 358). Making HTTPS mandatory for our endpoints is our own (sound) decision.
- (b) Quote: "A webhook delivery is considered successful if it was responded to with a `2xx` status code" / "A recommended request timeout value for webhooks is somewhere between 15 and 30s." / "`410 Gone`: ... Sender should disable the webhook endpoint, and stop sending it messages."
- (c) `standard-webhooks-spec.md` lines 293-370.
- (d) [secondary/web]

## ENGINEERING IMPLICATIONS

### 1. SGO directory, seeding and labels
1. Do not seed any real organization with an "approved", "listed" or "eligible" label. No official IRS or Texas list exists today (fact 21). If real names are shown at all before the IRS list exists, use a label with the same meaning as the market's wording: "Says it will serve Texas — not on an official list" (fact 22). Safer for v1: seed only clearly fictional sandbox SGOs, flagged `is_sandbox = true`, with an EIN field that cannot collide with a real EIN format in production data.
2. Model listings per State and per calendar year, because the statute ties SGO status to "the list submitted for the applicable covered State ... for the applicable year" (fact 18). Suggested record: `sgo(ein, legal_name, address, phone, exempt_status: recognized | pending)` plus `sgo_listing(ein, state, calendar_year, list_source: irs_sgo_list | state_public_list | self_announced | sandbox, listed_on, removed_on, source_url, source_fetched_at, source_sha256)`. The first five SGO fields mirror what a State must send the IRS (fact 17).
3. Listing status enum for the UI: `on_irs_list` (credit-eligible badge allowed), `removed` (with date; block new designated gifts from that date), `state_listed_not_on_irs_list` (possible because of the consent rule, fact 15 — show "cannot confirm on the IRS list" and get counsel's view before taking a designated gift), `self_announced` (pledge or sandbox only), `sandbox`. **[FACT-CHECK] Badge wording:** show what was verified — "On the IRS SGO list as of <date checked>" — not "credit-eligible" or "eligible". Listing is necessary but not sufficient for a donor's credit: the gift must be designated as a qualified contribution, the credit is nonrefundable and reduced by State credits (fact 7), and the proposed reliance rule has exceptions for a donor who knew of non-compliance (fact 14, proposed-reg lines 5075-5086).
4. Hard gates on a section 25F-designated gift, all evaluated at payment time: date is on or after 2027-01-01; the SGO has an `on_irs_list` listing for the gift's calendar year in a covered State; no removal date on or before the gift timestamp (fact 14). Store the evidence used: the list snapshot hash and fetch time. Before those gates can pass, offer only sandbox gifts or non-binding pledges (ACE and SGO Desk both use pre-2027 "commit"/"pledge" language: fact 23, and SGO Desk's step "Open for pledges" / "Collect donor commitments in 2026 so gifts can be processed on January 1, 2027.", `$S/sources/sgodesk.txt` lines 108-109). Also record the State the gift is allocated to (fact 75), and treat IRS-initiated removal the same as State removal (fact 80).
5. Build the IRS-list sync as a replaceable adapter. Its format is unknown (fact 21). It must handle entries shown as removed with a removal date (fact 16), organization by State, and multistate SGOs. It must also handle additions during the year: lists can be replaced or supplemented until the deadline, and pending-exemption organizations are added later (fact 18, fact-check note). Until a machine-readable list exists, support a manual admin import with the same schema and a required source URL.
6. Add a State-participation table rather than a Texas constant: `state_participation(state, calendar_year, advance_election_on_irs_list: bool, as_of_date, sgo_list_submitted: unknown | yes | no, source_url)`. Seed 2027 from the 31 names in fact 1 with `as_of_date = 2026-11-13` and `sgo_list_submitted = unknown`. Never print a State count in copy without the as-of date (fact 12). 1. ### 5. Outbound webhooks (Standard Webhooks)
1. Send `webhook-id`, `webhook-timestamp` (integer seconds, refreshed on each attempt), `webhook-signature` (fact 56).
2. v1 signing: `v1,` + base64(HMAC-SHA256(key, `${id}.${timestamp}.${rawBody}`)). Generate a random 32-byte secret per endpoint, show it once as `whsec_` + base64, and store it encrypted. Never share a secret across SGOs or camps (fact 57).
3. Serialize the JSON body once, sign those exact bytes, and send those exact bytes (fact 59).
4. Rotation: allow two active secrets per endpoint and send both signatures space-separated during the overlap (fact 56).
5. `webhook-id` must be stable across retries and must not contain a full stop; use a prefixed random id such as `msg_...` (the spec warns that id and timestamp must not be user-controlled or contain `.`).
6. Body: `{ "type": "verification.decided", "timestamp": "<ISO 8601>", "data": { ...ids, status, urls... } }`; event types full-stop-delimited using `[a-zA-Z0-9_]`; payload under 20 kb; thin by default (fact 60). Let each endpoint subscribe to event types.
7. Delivery worker: success on 2xx only; do not follow redirects; 15 to 30 s timeout; backoff with jitter over about three days (the spec's example schedule ends at 75 h 35 m); disable on `410`; throttle on `429`/`502`/`504`; honor `retry-after`; email the owner and disable after sustained failure (fact 61). Keep a delivery log with manual replay in the dashboard.
8. Endpoint URL validation: HTTPS only; resolve and block private, loopback, link-local and metadata IP ranges at send time (SSRF), including after DNS re-resolution (fact 61).
9. Consumer docs and sample code: verify with the raw body, constant-time compare, 5-minute tolerance, dedupe on `webhook-id` (fact 59). Add a CI test that verifies our signatures with the reference `standardwebhooks` package (fact 62).
10. Asymmetric `v2a` is optional later; if added, follow the endpoint-id rule exactly (fact 58).

### 6. ZIP / address -> county -> HUD area
1. Ask for a street address, not just a ZIP. For 569 of 1,992 Texas ZCTAs a ZIP alone does not fix the median, and for 692 it does not fix the county (facts 66-67).
2. Resolution order: (i) server-side Census Geocoder call with `layers=Counties`, read `Counties[0].GEOID`; (ii) if exactly one match and `STATE == "48"`, map county FIPS -> HUD area via the HUD file (`fips[:5]`); (iii) on zero or multiple matches, fall back to the ZCTA table: if the ZIP maps to one county, or to several counties in the same HUD area, accept it with `geo_method = "zip_single_area"`; otherwise ask the parent to pick the county from the candidate list and set `needs_review` if they cannot (fact 71). Never auto-pick the largest-area county for a threshold decision: in 245 Texas ZCTAs the largest county covers less than 75% of the land (fact 66), and land area is not population.
3. Record in the evidence pack: `geo_method` (geocoder | zip_single_county | zip_single_area | parent_selected | reviewer_set), county FIPS, HUD area code, Geocoder benchmark and vintage names, matched address string, and the Census file name.
4. Loader rules for the ZCTA file: open as `utf-8-sig`; split on `|`; drop rows with empty `GEOID_ZCTA5_20`; keep ZIP and FIPS as zero-padded strings; keep rows where `GEOID_COUNTY_20` starts with `48` but remember six ZCTAs also touch another State (facts 63-66). Unit tests: 78701 -> 48453 only; 78610 -> 48055, 48209, 48453 (same HUD area); 75494 -> four counties in four HUD areas; 77001 -> not found; 73949, 79837 and 88430 -> flagged as mostly out of State.
5. Unknown ZIP (not a ZCTA, or created after 2020): require the Geocoder path or a parent-selected county (fact 68).
6. Geocoder operations: call from the server (no CORS); cache by normalized address; set a timeout and treat failure as "fall back", not "ineligible"; do not send the student's name or any other field, only the address; rate limits are undocumented, so add a small client-side limiter and a circuit breaker (fact 72). `Public_AR_Current` and `Current_Current` drift over time; county boundaries in Texas are stable, but log the names anyway.
7. The HUD-USPS ZIP crosswalk (which has residential-address ratios and would be a better weight than land area) could not be verified today: `https://www.huduser.gov/portal/datasets/usps_crosswalk.html` returned HTTP 202 with an empty body. Treat it as an unverified possible upgrade.
